Desktop app launcher

Open a native JavaFX app in a chosen environment, straight from a web link.

Launches need a token signed by this server, naming the environment. Pick an environment and the server signs a token for that environment and version, then the desktop app opens. Another site reusing the link has no valid token and is rejected.

Launch by environment Production, UAT and the dev environments, each with its own link scheme and launcher install. Published versions What is in the artifact repository, and which version each environment launches.

One-time setup

Each environment registers its own link handler once, with no admin rights:

java -jar dist/fxsuite/FxSuite-prod.jar --register
java -jar dist/fxsuite/FxSuite-dev.jar  --register --env=dev1

That registers fxsuite-prod:// and fxsuite-dev1:// for your user account only (HKEY_CURRENT_USER), so a click starts that environment's launcher with no IT approval and no UAC prompt.

What happens on a launch

  1. The page asks the server for a token: GET /token?app=hello&env=<env>.
  2. The server signs a short-lived token naming the environment, app, version and the artifact's SHA-256, with that environment's private key.
  3. The browser hands fxsuite-<env>://launch/hello?tok=… to Windows, which starts that environment's launcher.
  4. The launcher checks the token and that it names its environment, downloads that exact version, checks its hash, and opens it.

Why another site can't launch anything

A link handler never learns which site opened it, so the launcher doesn't check the site. Trust comes from the signature: only this server holds the signing keys. Three separate checks keep environments apart: the link scheme, the per-environment signing key, and the signed environment name (which is what separates dev1 from dev2, since they share a key).
